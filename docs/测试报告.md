## 四、发现的问题

### ✅ P0-1 路由注册直接 panic —— 已修复

> **状态:已修复**。生成器新增路由冲突检测,在生成阶段即中止并精确定位;
> 同时修正了 yaml 里的 3 处冲突配置,服务现已能无 panic 启动。

**现象**

```
panic: ':id' in new path '/users/:id/detail' conflicts with existing
       wildcard ':userId' in existing prefix '/users/:userId'
panic: handlers are already registered for path '/orders'
panic: handlers are already registered for path '/articles/:id'
```

**根因**:gin 要求同一层路径段上的通配符**名字必须一致**,且同一 `METHOD+PATH` 只能注册一次。
代码生成器把接口按 yaml 文件/领域分组,不同领域各自定义路径,**完全不做跨领域路由冲突检测**。

实际冲突清单:

| 冲突路径 | 冲突方 | 处理方式 |
|---|---|---|
| `GET /orders` | `array.yaml` 的 `GetOrderList` vs `order.yaml` 的 `ListOrders` | order 列表改为 `/user-orders` |
| `GET /articles/:id` | `edge.yaml` 的 `GetArticle` vs `article.yaml` 的 `GetArticleById` | 文章详情改为 `/cms-articles/:id` |
| `/users/:id/detail` | `nested.yaml` vs `user.yaml` 的 `/users/:userId` | `nested.yaml` 参数名统一为 `:userId` |
| `GET /health` | `edge.yaml` 的 `HealthCheck` 占用运维常用路径 | 运维接口改为 `/_ops/health` |

**修复内容**

1. **生成期门禁**(`internal/handler/route_check.go`):`RunAll` 在生成前检测两类冲突,
   发现即中止,错误信息指出是哪两个 yaml 文件的哪个接口冲突。
2. **跨配置检测**(`internal/handler/route_existing.go`):一个工程可能由多份配置先后生成,
   各自单跑都合法、合到一起才冲突。因此还会扫描目标工程里已存在的 `*_router.go`,
   把历史路由一起纳入比对,并顺带揪出历史遗留的冲突。
3. **对外 API**(`pkg/codegen`):`ScanRouteConflicts` / `FormatRouteConflicts`,
   供装配层在启动前自检,把手工改坏的路由变成可读提示而不是 panic。

**修复效果**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 服务启动 | panic 退出 | 正常启动,`路由自检: 通过` |
| 可用路由数 | 46(3 个领域被跳过) | **58** |
| 冲突暴露时机 | 服务启动时 panic | **生成时中止**,报错指出具体 yaml 与接口 |

### ✅ P1-1 生成的请求结构体没有任何校验标签 —— 已修复

> **状态:已修复**。生成器按字段类型自动推导 `binding` 标签,
> 无需在 yaml 中显式声明。

**修复前**:67 个请求字段中 `binding` 标签数量为 **0**。

**修复后**:67 个字段 **100% 覆盖**。

```go
type CreateUserReq struct {
    Name     string        `json:"name" form:"name" binding:"required,max=255"`
    Age      int           `json:"age" form:"age" binding:"omitempty,gte=0"`
    Height   float64       `json:"height" form:"height" binding:"omitempty,gte=0"`
    Enabled  bool          `json:"enabled" form:"enabled" binding:"omitempty"`
    Birthday time.Time     `json:"birthday" form:"birthday" binding:"omitempty"`
    Nickname string        `json:"nickname" form:"nickname" binding:"required,max=255"`
}
```

**推导规则**

| 字段形态 | 生成的标签 |
|---|---|
| 关键标识(name / title / userName / password / phone / email) | `required,max=255` |
| 其他 string | `omitempty,max=255` |
| 整型 / 浮点 | `omitempty,gte=0` |
| bool | `omitempty` |
| 嵌套对象 / 切片 | `omitempty,dive` |
| 时间 / file | `omitempty` |

**两个设计取舍**

1. **必填判定按"完整的词"而非后缀**。最初用 `strings.HasSuffix(tag, "name")`,
   结果 `nickname`(昵称,本应可选)被误判为必填,合法请求直接被拒。
   改为取末段单词(`userName` → `name`、`nickname` → `nickname`)后修正。

2. **切片与嵌套对象用 `omitempty` 而非 `required`**。yaml 语法无法区分
   "必填数组"与"可选数组",一律强制必填会误拒合法请求(如可选的附件列表),
   因此只校验"传了之后是否合法"。

**实测拦截效果**

```
POST /api/v1/products  {"title":"X","price":-5}
  → 400  Field validation for 'Price' failed on the 'gte' tag

POST /api/v1/users     {"age":30}
  → 400  Field validation for 'Name' failed on the 'required' tag

POST /api/v1/users     {"name":"aaa...(300字符)","age":20}
  → 400  Field validation for 'Name' failed on the 'max' tag
```

### ✅ P1-3 HTTP 状态码始终为 200 —— 已修复

> **状态:已修复**。绑定/参数类错误返回 400,业务处理失败返回 422,成功 200。

**修复前**:所有错误(含参数错误、404、500)统一返回 `HTTP 200`。

**修复后**

```go
func (u *UserHandler) CreateUser(c *gin.Context) {
    var req request.CreateUserReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, response.NewErrorResponse[any](
            errorutil.ParamsError.WithMessage(err.Error())))
        return
    }
    data, err := u.userService.CreateUser(c, req)
    if err != nil {
        c.JSON(errorutil.HTTPStatusOf(err), response.NewErrorResponse[any](err))
        return
    }
    c.JSON(http.StatusOK, response.NewSuccessResponse[res.CreateUserRes](data))
}
```

`errorutil.HTTPStatusOf` 按错误来源判定:客户端引起的错误(参数/绑定类)→ 400,
业务处理失败 → 422。

**实测状态码分布**

| 场景 | 状态码 | 响应 |
|---|---|---|
| 正常创建 | 200 | `{"code":0,...}` |
| 缺必填字段 | **400** | 指出具体字段与规则 |
| 非法 JSON | **400** | `invalid character 'b' ...` |
| 路径参数非数字 | **400** | `strconv.ParseInt: parsing "abc": invalid syntax` |
| 资源不存在 | **422** | `资源不存在: 用户 id=99999` |
| 数组元素校验失败 | **422** | `items[0].count 不能小于 1(当前 0)` |

**附带收益**:错误信息不再统一为"参数错误",
而是带上 `err.Error()` 的具体原因,便于定位。

### ✅ P1-5 生成器不生成 path 参数的类型信息 —— 已修复

> **状态:已修复**。`@Param` 行尾追加 `format(...)` 属性。

**修复前**

```go
// @Param orderId path integer true "orderId"
```
swagger 输出只有 `type: integer`,前端拿不到具体宽度。

**修复后**

```go
// @Param orderId path integer true "orderId" format(int64)
```
```yaml
- description: orderId
  format: int64
  in: path
  name: orderId
  required: true
  type: integer
```

**踩坑**:`format(...)` **必须放在描述之后**。最初写成
`integer format(int64) true "orderId"`(把 format 拼在类型后面),
swag 直接报 `cannot find type definition: integer format(int64)` 并中止生成。

格式映射遵循 OpenAPI 惯例:

| Go 类型 | swagger type | format |
|---|---|---|
| int / int8 / int16 / int32 | integer | int32 |
| int64 / uint* | integer | int64 |
| float32 | number | float |
| float64 | number | double |
| string / bool | string / boolean | 无 |

**实测**:36 个 path/query 参数全部带上 format(25 个 int64 + 6 个 int32 等)。

### ✅ 额外修复:swag 无法解析 `time.Duration`

**现象**:`swag init` 报
`[lastEdit]: cannot find type definition: time.Duration`,**整个文档生成失败**。

**原因**:`time.Duration` 底层是 `int64`,但 swag 不认识这个命名类型。

**修复**:生成器为 `time.Duration` 字段自动追加 swaggertype 标签:

```go
LastEdit time.Duration `json:"lastEdit" swaggertype:"integer"`
```

这是 swag 官方支持的机制,生成后该字段输出为 `type: integer`。
