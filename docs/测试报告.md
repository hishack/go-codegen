## 四、发现的问题

### 🔴 P0-1 路由注册直接 panic,服务无法启动

**现象**

```
panic: ':id' in new path '/users/:id/detail' conflicts with existing
       wildcard ':userId' in existing prefix '/users/:userId'
panic: handlers are already registered for path '/orders'
panic: handlers are already registered for path '/articles/:id'
```

**根因**:gin 要求同一层路径段上的通配符**名字必须一致**,且同一 `METHOD+PATH` 只能注册一次。
代码生成器把接口按 yaml 文件/领域分组,不同领域各自定义路径,**完全不做跨领域路由冲突检测**。

实际冲突清单:

| 冲突路径 | 冲突方 |
|---|---|
| `GET /orders` | `array.yaml` 的 `GetOrderList` vs `order.yaml` 的 `ListOrders` |
| `GET /articles/:id` | `edge.yaml` 的 `GetArticle` vs `article.yaml` 的 `GetArticleById` |
| `GET /users/:id/detail` | `nested.yaml` vs `user.yaml` 的 `/users/:userId`(通配符名不同) |
| `GET /health` | `edge.yaml` 的 `HealthCheck` 占用运维常用路径 |

**影响**:44 条路由中 3 个领域(共 12 条路由)完全无法注册,服务直接崩溃。

**复现**:`cd example && go run .`

---

### 🔴 P0-2 路径参数解析失败后缺少 `return`,输出双段 JSON

**现象**

```http
GET /users/abc
```
```json
{"code":40000,"message":"参数错误","data":null}{"code":40003,"message":"数值超出允许范围: userId 必须为正数","data":null}
```

**根因**:生成的 handler 里

```go
userId, err := strconv.ParseInt(userIdStr, 10, 64)
if err != nil {
    c.JSON(http.StatusOK, response.NewErrorResponse[any](errorutil.ParamsError))
    // ← 这里缺 return
}
data, err := u.userService.GetUser(c, userId)   // 继续执行
```

响应被写了两次。**在 10 个 handler 文件中共发现 21 处**:

| 文件 | 处数 | 文件 | 处数 |
|---|---|---|---|
| user_handler.go | 5 | edge_handler.go | 4 |
| product_handler.go | 3 | order_handler.go | 2 |
| nested_handler.go | 2 | 其余 5 个文件各 1 处 | 5 |

**影响**:任何非数字路径参数都会产生非法 JSON,前端 `JSON.parse` 直接抛异常。
更糟的是请求仍会继续进入 logic 层,产生无意义的业务调用。

---

### 🟡 P1-1 生成的请求结构体没有任何校验标签

所有 `request/*.go` 中 `binding:"..."` 标签数量为 **0**。

```go
type CreateUserReq struct {
    Name     string        `json:"name" form:"name"`   // 无 required / min / max
    Age      int           `json:"age" form:"age"`     // 无 gt=0,lte=150
    Email    string        `json:"email" form:"email"` // 无 email 格式校验
}
```

**影响**:字段级校验完全依赖 logic 层手写。生成器既然已经知道字段类型(比如 `age: int`),
完全可以生成 `binding:"required"`、`binding:"gte=0,lte=150"` 这类标签,
让 gin 在 ShouldBind 阶段就拦掉非法请求,不必把脏数据传给业务层。

---

### 🟡 P1-2 重复路径的接口被静默生成

`article.yaml` 里 `GetArticleStats` / `GetArticleStats1` / `GetArticleStats2` **path 完全相同**(`/articles/stats`),
生成器照单全收,生成了 3 套结构体(`GetArticleStatsRes` / `...1Res` / `...2Res`)和 3 个方法。

**影响**:路由树里三条记录争同一个位置,gin 只认第一条,另外两个方法永远不会被调用。
结构体还白白膨胀了 2 份。

---

### 🟡 P1-3 HTTP 状态码始终为 200,错误语义丢失

所有错误响应(包括参数错误、404、500)统一返回 `HTTP 200`,仅在 body 里用 `code` 区分。

```json
HTTP/1.1 200 OK
{"code":40000,"message":"参数错误","data":null}
```

**影响**:
- 违反 RESTful 语义
- 网关/APM/监控无法按状态码统计错误率
- 前端拦截器、浏览器缓存、CDN 都会误判
- `GET /users/abc` 这类场景返回 200 尤其危险

---

### 🟡 P1-4 业务错误码映射不一致

| 场景 | 实际 code | 应有 code |
|---|---|---|
| 参数错误(ShouldBind 失败) | `40000` | 40000 ✅ |
| 路径参数解析失败 | `40000` + 后续 `40003` | 40000(但应只输出一次) |
| JSON 语法错误 | `50000` | 40000 |
| Query 数字转换失败 | `50000` | 40000 |

`errorutil.ConvertError` 把所有非 `BusinessError` 的错误都归为 `SystemError(50000)`,
导致「客户端传了坏 JSON」这种明显的 400 场景被记成服务端故障。

---

### 🟡 P1-5 生成器不生成 `@Router` 的参数类型信息

`/orders/:orderId` 里 `:orderId` 是自定义命名,但 swagger 里生成的是 `/orders/{orderId}` 且未标注类型。
对于 `(int64)` 这类标注,swagger 输出没有 `format: int64` 或明确说明,前端拿不到类型提示。

---

### 🔵 P2-1 空实现返回 `null` 而非空数组

未实现业务逻辑的领域(如 `edge` 的 `SearchUser`)返回:

```json
{"code":0,"data":{"total":0,"list":null}}
```

`list` 为 `null` 会让前端 `list.map()` 直接报错。生成器应为切片字段初始化为空数组。

---

### 🔵 P2-2 `code` 常量硬编码在 errorutil,业务无法自定义错误码段

`errorutil` 只提供 `ParamsError(40000)` / `SystemError(50000)` 等固定几个,
业务特有的错误(如"订单已发货不可取消")只能复用或硬编码数字,不利于错误码治理。

---

### 🔵 P2-3 无统一的请求追踪/日志中间件

生成的 handler 直接调用 service,没有 requestID 注入、访问日志、耗时统计。
多领域拆分后排查问题会很困难。

---

## 五、代码生成器改进建议

### 优先级 P0(必须修)

**1. 增加跨领域路由冲突检测**

在生成前做全局检查,发现冲突直接报错并给出定位:

```
order.yaml 的 ListOrders (GET /orders) 与 array.yaml 的 GetOrderList (GET /orders) 路由重复
nested.yaml 的 Xxx (/users/:id/detail) 与 user.yaml 的 Yyy (/users/:userId) 同层通配符名不一致
```

同时建议**同前缀下的路径参数名统一**(如同为 `/users/:xxx`),从源头避免 gin 的限制。

**2. 修复路径参数解析缺 `return` 的模板**

`internal/handler/handler_gen.go` 里 `strconv.ParseInt` 的错误分支模板补上 `return`。
这是一行改动,但影响 21 处生成代码的正确性。

### 优先级 P1(强烈建议)

**3. 为请求字段生成 `binding` 校验标签**

生成器已知字段类型,可按类型自动推导:

| yaml 类型 | 建议标签 |
|---|---|
| `string`(命名含 name/title) | `binding:"required"` |
| `int` / `int64` | `binding:"omitempty,gte=0"` |
| `float64` | `binding:"omitempty,gte=0"` |
| `bool` | `binding:"omitempty"` |
| 嵌套对象/数组 | `binding:"required"` |

也可在 yaml 中支持显式约束:

```yaml
CreateUser:
  req:
    name: string # 必填,最长 32
    age: int    # 0-150
```

**4. 增加重复 path 检测**

同一 `METHOD + PATH` 重复时直接报错,而不是生成三个争抢路由的方法。

**5. 改进 HTTP 状态码**

让生成的 handler 根据错误类型设置状态码:

```go
c.JSON(http.StatusBadRequest, response.NewErrorResponse[any](err))
```

并区分 `BindError`(400)与 `BusinessError`(按 code 映射)。

**6. 统一错误码映射**

在 `ConvertError` 里增加对 `json.UnmarshalTypeError`、`strconv.NumError` 等类型识别的判断,
统一映射到 `ParamsError(40000)`,而不是一律 50000。

### 优先级 P2(可选改进)

**7. 为切片字段生成空数组初始化**,避免 `null`。

**8. 支持自定义错误码段**,如配置 `codeBase: {order: 41000, user: 42000}`。

**9. 生成请求追踪中间件**,或至少在 README 中给出推荐中间件示例。

**10. 支持接口分组前缀**,如在 yaml 中声明 `group: /api/v1`,生成时统一加前缀,
避免多领域路径散落冲突。

## 六、测试结论

### 生成器做得好的地方

1. **七层分层清晰**,model/service/logic/handler/router/ts 各司其职
2. **注释三端贯通**:yaml 的 `#` 注释 → Go 字段注释 → swagger `@Summary`/`@Param` → TS jsdoc,设计非常好
3. **类型覆盖完整**:基础类型、时间、数组、对象、对象数组、map、file 全支持
4. **增量合并可靠**:重复生成幂等(`新增 0`),且严格保留用户手写代码
5. **结构体命名可预测**:`<父结构体><字段大驼峰>`,对象数组加 `Item` 后缀
6. **swagger 生成完全正常**,55 个接口、40 个结构体,嵌套提升正确
7. **handler 参数获取正确**:path/query/body/form 四种来源都能正确绑定

### 必须修复的问题

| 编号 | 问题 | 严重度 | 修复成本 |
|---|---|---|---|
| P0-1 | 路由冲突导致服务无法启动 | 🔴 阻塞 | 中(需全局检测逻辑) |
| P0-2 | 路径参数解析缺 `return`,输出双段 JSON | 🔴 高 | 低(改模板一行) |
| P1-1 | 请求字段无 `binding` 校验标签 | 🟡 中 | 中 |
| P1-2 | 重复 path 静默生成 | 🟡 中 | 低 |
| P1-3 | 错误响应一律 HTTP 200 | 🟡 中 | 低 |
| P1-4 | 业务错误码映射不一致 | 🟡 中 | 低 |

### 伪实现验证价值

本轮补齐的 30 个 logic 方法覆盖了:
- 必填/长度/数值区间校验
- 唯一性约束(标题、档位)
- 状态机流转(订单取消)
- 幂等设计(标记已读)
- 频率限制(短信 1 分钟)
- 白名单(扩展名、scene、档位)
- 服务端计算金额(不信任前端)
- 并发安全(读写锁)

这些实现证明**生成的分层结构足以支撑真实业务开发**,骨架本身没有问题,
问题集中在生成器模板的严谨性上。
